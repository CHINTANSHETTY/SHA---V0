### 1.2 Purpose & Necessity of HKDF in KDR-CA-AEAD
In the baseline legacy system (`SHA---V0`), key stream material was generated by repeatedly concatenating raw `SHA-512(password)` hex strings. This caused deterministic periodic key stream reuse across records encrypted under the same password ($C_1 \oplus C_2 = T(P_1) \oplus T(P_2)$).

HKDF (RFC 5869 / NIST SP 800-56C) resolves this critical vulnerability by:
1. Extracting uniform pseudorandomness from low-entropy master passwords and random salts ($S$).
2. Expanding the pseudorandom key into cryptographically independent sub-keys ($K_r, K_c, K_a$) bound to unique nonces ($N$).

## 3. HKDF Technical Overview

HKDF is a two-step HMAC-based key derivation function following RFC 5869:

### 3.1 Extract Step ($PRK = \text{HMAC-Hash}(Salt, IKM)$)
Extracts uniform pseudorandomness of fixed length (32 bytes for SHA-256) from Input Keying Material ($IKM$) using a Salt ($S$). If no salt is provided, a zero-filled byte string of HashLen (32 bytes) is substituted per RFC 5869 Section 2.2.

### 3.2 Expand Step ($OKM = \text{HMAC-Hash}(PRK, info \parallel counter)$)
Expands $PRK$ to output keying material ($OKM$) of arbitrary requested byte length $L \le 255 \times 32 = 8160$ bytes by chaining HMAC-SHA256 iterations with an 8-bit counter index.

### 3.3 Key Derivation vs. Password Hashing
- **HKDF**: Optimized for fast derivation of independent sub-keys from high/medium entropy seeds or salts.
- **Argon2id / PBKDF2**: Slow, memory-hard KDFs designed specifically to slow down dictionary attacks on user passwords. In KDR-CA-AEAD, Argon2id protects database login passwords (`database/db_manager.py`), while HKDF expands session sub-keys (`crypto/primitives/hkdf.py`).

## 6. HKDF Module Design Specification

### 6.1 Architectural Design
The module `crypto/primitives/hkdf.py` exposes three public API functions (`hkdf_extract`, `hkdf_expand`, `hkdf`) built strictly on standard `hmac` and `hashlib` libraries using `hashlib.sha256`.

```
                  [ ikm (bytes) ] + [ salt (bytes) ]
                                 │
                                 ▼
                         hkdf_extract()
                                 │
                                 ▼
                          [ prk (bytes) ]
                                 │
                                 ▼
             hkdf_expand(prk, info, length)
                                 │
                                 ▼
                     [ okm (length bytes) ]
```

### 6.2 Validation Rules & Exceptions
- `ikm` must be a non-empty `bytes` or `bytearray` object. Raises `ValueError` if empty or `TypeError` if invalid type.
- `salt` defaults to `b"\x00" * 32` if `None` or empty.
- `prk` must be at least 32 bytes for SHA-256. Raises `ValueError` if less than 32 bytes.
- `length` must satisfy $1 \le length \le 8160$ bytes ($255 \times 32$). Raises `ValueError` if out of bounds.

## 7. Functions Planning

### Function 1: `hkdf_extract(salt: bytes | None, ikm: bytes) -> bytes`
- **Purpose**: Computes pseudorandom key ($PRK$) from input keying material.
- **Inputs**: `salt` (optional `bytes`), `ikm` (required `bytes`).
- **Outputs**: 32-byte binary `bytes` object ($PRK$).
- **Exceptions**: `ValueError` if `ikm` is empty. `TypeError` if input types are not bytes-like.
- **Time Complexity**: $O(|IKM| + |Salt|)$.
- **Space Complexity**: $O(1)$ (32-byte digest).

### Function 2: `hkdf_expand(prk: bytes, info: bytes | None, length: int) -> bytes`
- **Purpose**: Expands $PRK$ into output keying material ($OKM$) of length bytes.
- **Inputs**: `prk` (32-byte `bytes`), `info` (optional `bytes`), `length` (`int`).
- **Outputs**: `bytes` object of exact byte length `length`.
- **Exceptions**: `ValueError` if `prk` length < 32 bytes or `length` out of range $[1, 8160]$.
- **Time Complexity**: $O(\lceil length / 32 \rceil \times (|info| + 32))$.
- **Space Complexity**: $O(length)$.

### Function 3: `hkdf(ikm: bytes, length: int, salt: bytes | None = None, info: bytes = b"") -> bytes`
- **Purpose**: Convenience function executing `hkdf_extract` followed by `hkdf_expand`.
- **Inputs**: `ikm`, `length`, `salt`, `info`.
- **Outputs**: Derived keying material (`bytes`).

## 9. Exception Planning

- **`ValueError`**: Thrown for invalid length arguments ($L \le 0$ or $L > 8160$) or empty input keying material ($IKM$).
- **`TypeError`**: Thrown when string inputs are passed instead of explicit `bytes` or `bytearray`.

---

## 10. Logging Strategy

- **What to Log**: Module invocation events, requested expansion length, execution timestamps.
- **What NOT to Log**: **NEVER log `ikm`, `salt`, `prk`, or derived output keys (`okm`)**. Logging key material introduces catastrophic credential leakage vulnerabilities.
- **Log Levels**: `DEBUG` for function entry/exit; `WARNING` for non-standard parameter sizes.

---

## 11. Security Requirements & Hardening

1. **Input Validation**: Strict type enforcement (`bytes` or `bytearray`). No implicit string-to-byte encoding within primitives.
2. **Memory Protection**: Local key variables isolated within function local scope for rapid garbage collection.
3. **Side-Channel Considerations**: Uses standard `hmac.new` and `hmac.compare_digest` to prevent timing analysis.
4. **RFC 5869 Conformance**: Strict adherence to RFC 5869 Section 2.2 and Section 2.3 specifications.
