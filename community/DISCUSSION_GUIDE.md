# Community Discussion & Communication Guidelines

This document outlines community etiquette, communication channels, best practices for technical discussions, and guidelines for requesting features or architectural changes in **KDR-CA-AEAD**.

---

## 1. Code of Conduct & Etiquette

We are committed to providing a welcoming, inclusive, and professional environment for all contributors and researchers.

- **Be Respectful**: Treat all community members with courtesy and professional respect regardless of background or experience level.
- **Constructive Feedback**: Offer constructive, evidence-based feedback on pull requests and technical proposals.
- **Academic Integrity**: Maintain high standards of scientific rigor when discussing benchmark results, security claims, and cryptanalysis.

---

## 2. Communication Channels

| Channel | Purpose | Link / Contact |
| :--- | :--- | :--- |
| **GitHub Discussions** | Q&A, general ideas, architectural proposals, research chat | [Repository Discussions](https://github.com/CHINTANSHETTY/SHA---V0/discussions) |
| **GitHub Issues** | Bug reports, test failures, feature requests | [Repository Issues](https://github.com/CHINTANSHETTY/SHA---V0/issues) |
| **Security Email** | Private disclosure of potential security vulnerabilities | `security@kdrca-research.org` |

---

## 3. Best Practices for Technical Discussions

1. **Search Before Asking**: Check existing issues, FAQs, and documentation before starting a new discussion thread.
2. **Provide Reproducible Snippets**: When asking code questions, include self-contained minimal working examples (MWEs).
3. **Reference Specific Specifications**: Cite relevant standard documents (e.g., RFC 5869, NIST SP 800-56C) or paper sections when discussing cryptographic modifications.

---

## 4. Proposing Architectural Changes

When proposing major architectural modifications (e.g., changing HKDF parameters, adding 2D CA rules):
1. Open a **GitHub Discussion** under the "Ideas" category.
2. Provide theoretical justification, security analysis impact, and performance trade-offs.
3. Allow 7 days for maintainer and community review before submitting code PRs.
